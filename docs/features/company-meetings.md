# Company meetings

A **meeting** is a live call with your team where people and AI profiles sit in
the same room. It is not a chat with one assistant: the meeting has a
participant list, a transcript, a recording, notes and minutes, and the
follow-ups decided in it can become tasks — optionally run or scheduled before
the page is closed.

The meeting chat is the single source of truth for the conversation. Every
human utterance, every AI profile answer and every meeting notice is a normal
message of that chat, so the transcript can be searched, exported and reused
like any other conversation.

## Starting a meeting

| Entry point | What it does |
| --- | --- |
| **Main menu → New meeting** | Opens the setup dialog: name, agenda, people, AI profiles, board to review and meeting behaviour. |
| **A channel → Meet** | Calls the channel. Team members are pre-selected, the team's profiles join as AI participants and the meeting is linked to the channel. |
| **Meet → Start with participants** | The same setup dialog from the meeting lobby. **Start call** still creates a quick meeting with just you. |
| **Invitation** | A started meeting appears as an **incoming meeting** card in every connected client. Join in one click or dismiss it. |

The setup dialog lets you choose:

* **People** — human users of the installation. They receive the invitation and
  join through the normal WebRTC mesh.
* **AI profiles** — profiles of the project. They appear immediately as virtual
  participants with their avatar and camera off; they need no browser or video.
* **Review board** — the board whose task status is given to the profiles and to
  the minute taker.
* **Call a team** — pre-selects every member and every profile of a team.
* **Meeting behaviour** — recording, automatic minutes, live profile answers,
  live notes and how many profiles may answer a turn.

## The meeting room

* **Human participants** are camera-off by default. When the camera is off, the
  tile shows the user's avatar; a speaking participant is highlighted.
* **AI profiles** are camera-off tiles with the profile avatar and an `AI`
  badge. They are never WebRTC peers: no device, no camera, no microphone.
* **People / Chat / Notes / Browser** panels sit next to the call. The Chat panel
  is the associated meeting chat. The Notes panel shows the live transcript and
  the minutes.
* **REC** appears while the host records the mixed call audio.
* **Live captions** show the interim transcription of the microphone and who is
  speaking.

## Profiles in the conversation

Profiles take turns. `max_profile_turns` bounds how many profiles answer one
human turn, and mentions (`@analyst …`) pick a specific profile. Without a
mention the profiles that spoke least answer, so the whole team participates
instead of the same assistant answering every time.

A profile answer is:

1. generated with the profile's instructions, the meeting agenda, the recent
   transcript and a **fresh task-status snapshot**;
2. appended to the meeting chat with `user = <profile>` and a
   `meta_data.meeting` marker;
3. spoken aloud with the profile's configured voice (server TTS when configured,
   browser `SpeechSynthesis` otherwise).

`PASS` from the model means "I have nothing useful to add": nothing is stored
and the next profile may answer.

### Profiles stop when a person talks

Only one participant speaks at a time and **human speech always wins**:

* every client watches its own microphone level and sends a floor event when it
  starts and ends speech;
* the server marks the floor as taken by a human, **interrupts the profile that
  is talking** and marks its answer as interrupted;
* every client stops the profile audio immediately, and the remaining queued
  profiles are skipped.

The same rule applies between profiles: the scheduler speaks one answer at a
time, so profiles never talk over each other. The answer text is still kept in
the chat even when its playback is cut short.

## Recording and notes

The host records the call from its own browser: the local microphone, every
remote WebRTC stream and the synthesized profile voices are mixed into one
audio track. The file is uploaded when the meeting ends and can be replayed from
the summary page. Browsers without `AudioContext`/`MediaRecorder` simply skip the
recording; the meeting and the transcript keep working.

Notes are generated by the minute taker from the transcript and the task
snapshot:

* **at the end** when *Minutes at the end* is enabled,
* **on demand** from the Notes panel or the summary page,
* **during the meeting** when *Live notes* is enabled (refreshed after the
  configured interval).

The minutes contain a summary, key points, decisions and **action items** (owner,
suggested profile, priority, due date, scheduled instant, run now).

## From minutes to tasks

The meeting summary (`/:projectName/meet/:meetId/summary`) shows the attendees,
the recording, the minutes and the transcript. It is also the place to:

* select the action items and **Create tasks** on a board/column;
* **run the tasks immediately** (the normal project chat turn is started in the
  background for each created task);
* **schedule** them with a date/time (written to `Chat.wake_at`, which the
  autonomy runtime consumes).

Each created task links back to the meeting through its `meeting`/meeting id
tag, and the action item records the created task id so creating twice never
duplicates work.

## API

All routes are under `/api/meets`:

| Route | Purpose |
| --- | --- |
| `POST /initiate` | Create a meeting (participants, profiles, agenda, board, channel, settings). |
| `POST /join`, `POST /leave`, `POST /end` | WebRTC lifecycle. `end` starts the minutes when configured. |
| `GET /`, `GET /history`, `GET /{id}` | Live meetings, persisted meetings and one meeting. |
| `POST /{id}/participants`, `POST /{id}/invite`, `DELETE /{id}/participants/{name}` | Invite users, add/remove AI profiles. |
| `POST /{id}/chat` | Create/load the associated chat. |
| `POST /{id}/utterance` | Record a spoken/typed utterance and trigger the profiles. |
| `POST /{id}/floor` | Speech start/end (barge-in). |
| `GET /{id}/transcript`, `GET /{id}/notes` | Transcript and minutes. |
| `POST /{id}/notes` (alias `/minutes`) | Generate/refresh the minutes. |
| `POST /{id}/tasks` | Create/run/schedule tasks from the action items. |
| `POST /{id}/recording`, `GET /{id}/recording` | Upload/replay the call recording. |
| `POST /{id}/speech` | Synthesize a profile answer with its configured voice. |
| `POST /{id}/browser`, `POST /{id}/signal/*` | Shared co-browsing and WebRTC signalling. |

Socket.IO events use `codx-junior-meet` with `type`:
`initiated`, `started`, `joined`, `left`, `ended`, `participants`,
`participant-invited`, `transcript`, `floor`, `profile-turn`,
`profile-turn-end`, `minutes`, `recording`, `tasks-created`, `browser-session`.
The frequent events carry a **compact** meeting document; the transcript is
delivered one entry at a time and the full document is always available through
`GET /api/meets/{id}`.

## Storage

The live registry is in memory (a process-wide singleton). The durable meeting
document, the minutes and the recording live under the project's
`.codx/meetings/`:

```text
.codx/meetings/<meet_id>.json        meeting, transcript, minutes, recording ref
.codx/meetings/index.json            latest-meeting catalogue
.codx/meetings/recordings/<id>.webm  mixed call recording
```

The meeting chat is a normal chat stored in the project (`mode = "meet"`, board
`Meetings`, column `Live`) and linked from `Chat.meta_data.meeting`.

## Limitations

* The recording is mixed by the host's browser. If the host leaves before the
  end, the recording stops with it.
* Profile answers run through the project's normal model configuration; a
  profile with no model inherits the project default.
* Speech recognition depends on the browser (`SpeechRecognition` in
  Chrome/Edge). Firefox/Safari use the optional server transcription backend;
  text can always be typed in the meeting chat.
* Meeting documents are project-scoped: a meeting started in a project is stored
  and listed in that project.
