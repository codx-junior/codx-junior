# Kanban and tasks

The Kanban board is where humans plan the work and hand it to the AI.

![Kanban](/images/NOV2025/codx-junior-kanban.png)

## Boards

Each project can have several boards. A board has a name, a description, an optional remote URL and its columns (for example *Backlog*, *To Do*, *In Progress*, *Done*). Boards can be bookmarked and switched from the sidebar.

## Tasks are chats

Every card on a board is a [chat](/features/chats-and-agents). Opening a card opens the conversation, so a task can be discussed with the team, refined into a specification and executed by an agent, all in one place.

A task can have:

* a status, tags and assigned users,
* profiles and a model,
* linked files and attachments,
* checklists,
* **sub-tasks**, created by hand or generated by the AI from the parent task.

## Archiving tasks

Finished tasks do not have to weigh on the project forever. **Archiving** a task
compresses it and takes it out of the live tree:

```
.codx/tasks/
  <board>/<column>/<slug>.<chat_id>.json   live tasks (listed, searched, loaded)
  .archive/
    index.json                             archive catalogue (metadata only)
    <chat_id>.tar.gz                       the archived task (chat.json inside)
```

What archiving changes:

* the task **disappears from every listing, board, search, analytics and cost
  roll-up**, because `ChatManager.chat_paths` only discovers real chat files,
* it takes **a fraction of the space** (gzip on an indented chat JSON is
  typically 10-20x smaller), which matters on projects that reach hundreds of
  megabytes of task history,
* it can be **restored byte for byte** into the same board and column.

Listing an archived task is cheap: `index.json` stores only what is needed to
render it (name, board, column, status, dates, sizes), so nothing is
decompressed until a restore.

### From the UI and the API

| Route | What it does |
| --- | --- |
| `POST /api/chats/archive` | `{"chat_id": "...", "user": "me"}` → compresses the task |
| `POST /api/chats/restore` | `{"chat_id": "..."}` → brings it back to its board/column |
| `GET /api/chats/archived` | catalogue entries + `stats` (bytes before/after, ratio) |
| `GET /api/chats?include_archived=true` | also list archived tasks (metadata only) |
| `GET /api/chats/recent?include_archived=true` | same, paginated |

**Archived tasks are invisible unless you ask for them**: every listing endpoint
and every `ChatManager` method defaults to `include_archived=false`.

### From a profile (AI tools)

`project_manager` gained two actions, so an agent can tidy a board on its own:

* `project_manager(action="archive_task", chat_id="...")`,
* `project_manager(action="restore_task", chat_id="...")`,
* `project_manager(action="list_tasks", include_archived=true)` to review what is
  archived.

### Good practice

* Archive leaf tasks or a whole finished subtree: a parent whose cost rolls up
  into a root task should be archived after its children.
* Restoring is non destructive: the archive payload keeps the original file name,
  so the restored task is indistinguishable from one that was never archived.
* Deleting an archived task permanently is a deliberate act
  (`TaskArchive.forget(chat_id)`): archiving never deletes history.

## Views

Switch between the **board** view (columns and cards), a **grid** view with filters, and a **tree** view of tasks and sub-tasks. The Kanban panel is also available next to the conversation in [vibe coding](/features/vibe-coding).

## Templates

Mark a chat as a template to reuse it when creating new tasks.

## Global task search

Large boards hide work. The **Find** button in the Kanban toolbar (or
`Ctrl/Cmd+Shift+F`) opens a project-wide search over **every board and sprint**,
not only the board that is currently open.

The search runs on the server (`GET /api/kanban/search`) so it also finds tasks
outside the default 30-day chat window. Every whitespace-separated term must
match somewhere in the:

* task name and description,
* board, column, status and priority,
* profiles, people and tags,
* last message.

Results are scored (an exact title match first, then a title prefix, then the
metadata and messages) and can be filtered by board, status, priority, profile
and assignee. `Include done` is on by default; turn it off to focus on open work.
Use `↑` / `↓` and `Enter` to open a result without leaving the keyboard. A result
on another board switches the Kanban panel to that board before opening the card.

## Board manager

A board can associate a **profile** and let it review the board in the
background. Open **Board manager** in the board toolbar (or in *Board settings*)
to configure:

* **Manager profile** — the profile that reviews the board. Empty falls back to
  the board assistant and then to `ProjectManager`.
* **Mode** — `Apply changes` writes the actions, `Suggest only` records them in
  the report.
* **Review every** — the minimum interval between two automatic reviews.
* **Max actions per review** — a hard upper bound.
* **Include done** — closed tasks are sent as context but are never modified.
* **Instructions** — board-specific policy (for example *close tasks completed
  more than 7 days ago*, *move blocked cards to On hold*).

The background worker sends the profile a bounded snapshot of the board and asks
for a JSON decision. Supported actions are:

| Action | Effect |
| --- | --- |
| `move_task` | Move a kanban card to a column, or a sprint card to a status |
| `comment` | Add a comment to the task (an assistant message) |
| `close_task` | Set the status to done, progress 100 and move to the Done column when it exists |
| `update_task` | Change priority, due date, progress, assignees or tags |
| `create_task` | Create a follow-up task on the board |

Every action is validated before it is applied: the task must belong to the
board, the destination column must exist, and closed tasks, templates, channels
and cards owned by an active orchestration run are never modified. In *Suggest
only* mode nothing is written.

The **status panel** of the board manager shows the last run, next run, total
cost, the last report and the applied actions. **Run now** queues an immediate
review; the actual AI turn is executed by the background worker, so the HTTP
request returns immediately. If the worker is not running, the panel says so and
the review stays queued.

The manager is disabled by default. Enable it explicitly per board. The
background loop is controlled by `CODX_JUNIOR_BOARD_MANAGER` and
`CODX_JUNIOR_BOARD_MANAGER_TICK_SECONDS`; it can be turned off without disabling
the rest of the background services.

## Follow-up task queue

The **Follow-up** view is the cross-board queue of work: it is not a single
board but the latest tasks of the selected projects, ordered by recent activity.

* **Every filter is a checkable, searchable multi-select**: projects, boards,
  columns, statuses, priorities and assignees. They sit in one horizontal row
  and empty selection means "no filter".
* **Projects** start with the active project **and its children** selected;
  clearing the selection means "all visible projects".
* **Boards** lists only the boards of the selected projects, so the board filter
  can never point at a project that is out of scope.
* Every row shows the **latest message**, its author and time, an **unread
  replies** badge, and a **stopped/error** badge when the execution did not end
  cleanly (orchestration `run_status`, harness/execution status or the last
  assistant message error).
* Rows with no activity for `OLD_TASK_DAYS` (7 days) are dimmed and carry an
  `Nd` age badge; the exact timestamp stays in the `Last update` column. Age is
  never signalled by colour alone.

Unread and process state are computed while the task file is read in
`ChatManager` and carried as transient, non-persisted `Chat.task_*` fields. That
keeps the shared task files free of one user's read state.

## Board management and responsibility

Open **Board management** from the Follow-up toolbar, the Team view or the
kanban board's Follow-up panel. It lists every board of the selected projects
with its flow, effective responsible, task count, overdue count and unassigned
count.

Every board has a **responsible** (`responsible_kind` = `user` or `profile`,
`responsible_name`) and a **flow**:

| Flow | Statuses |
| --- | --- |
| `agile` (default) | `todo`, `doing`, `done`, `rejected`, `onhold` |
| `delivery` | `backlog`, `todo`, `doing`, `review`, `done`, `rejected` |
| `support` | `new`, `triage`, `waiting`, `resolved`, `closed` |
| `custom` | whatever the board defines |

Responsibility is **inherited**: a board without its own responsible uses the
nearest ancestor board's responsible. The effective source is shown in the UI
(`board`, `parent`, `assignee`, `team`, `default`), and the last fallback is the
`ProjectManager` profile, so no board is ever left without a responsible.

The board manager uses the responsible profile as its default reviewer and
receives the board flow in its instructions (agile/delivery/support rules and
the requirement that every task ends the review with a responsible, a next step,
or a terminal status). A human responsible is the accountable owner; only a
profile can run the background review automatically.

The API surface is `GET /api/tasks/boards` (boards + teams + effective
responsibility) and `PUT /api/tasks/boards` with
`{board_id, flow, responsible_kind, responsible_name, propagate_children}`.
